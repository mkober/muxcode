# Audible and Visual Announcement of Waiting Graph Gates

A `wait_human` gate halts a graph run until a person approves it. Arming one today produces four
signals, and **not one of them reaches a human who is not already looking at the right pane**:

| Signal today | Who it actually reaches |
|--------------|------------------------|
| `SendNoCC()` a `graph-approval` message | the **edit agent's inbox** — an agent, not a person |
| `Notify(session, "edit")` | the edit **pane**, via send-keys |
| `graph-gate-pending` lifecycle row | a log file nobody is tailing |
| Control pane switches to Pending Gates (MUX-108) | only if the user is watching that pane, in that session |

Every one is either agent-facing or **pull**-based. A user who walks away from the terminal — the
normal case while a build-test-review phase runs for several minutes — gets nothing. The run sits
`waiting` indefinitely, and because MUX-121 gives every phase its own gate, one missed announcement
stalls an entire multi-phase pipeline behind it.

This spec adds a **push** announcement aimed at the human: a spoken line generated by text-to-speech,
plus a visual indicator, fired when a gate begins waiting and **coordinated across every muxcode
session on the machine**.

## Context

### The gap is "push vs pull", not "no surface exists"

MUX-108 already built a good gate surface. `LoadPendingGates()` (`tui/graph_ui.go:141`) collects
every waiting `wait_human` node, `RenderGateQueueFrame()` draws the queue, and `checkGateSwitch()`
(`graph_ui.go:1434`) auto-switches the control pane to it. The dispatch comment in
`graph_exec.go:504` states the design intent plainly:

> Gate surfacing is the control pane's job: it switches itself to Pending Gates on the next tick
> (MUX-108). The graph popups were removed with the pane's arrival — no modal fallback remains.

That is correct **and** it is exactly the limitation. A pane that switches itself is only an
announcement to someone facing the screen. "No modal fallback remains" means there is deliberately
nothing that interrupts. This spec does not replace that surface — it adds the interrupt the surface
deliberately does not provide.

### Why cross-session is the hard part, not a bonus requirement

Sessions are fully independent: `BusDir()` returns `/tmp/muxcode-bus-<session>`, and **each session
runs its own daemon**. `DiscoverSessions()` (`bus/remote.go:24`) finds peers only by scanning `/tmp`
for `muxcode-bus-*`. `LoadPendingGates()` takes a single `session` argument and scans only that
session's runs — the gate queue is cross-**run** but single-**session** today.

So N sessions means N independent detectors. For a *visual* signal that is harmless: each session
paints its own pane. **For audio it is a defect**, because audio is a global, singular, serial
resource in a way no pane is:

- Two panes render simultaneously and both stay readable. Two utterances overlap and **neither is
  intelligible** — the user is worse off than with one, or with none.
- A pane is scoped to the session that owns it. Sound is not scoped to anything. A gate in session
  `alpha` is heard by a user attached to session `beta`, with no indication which session spoke.

Both consequences force the same two requirements: announcements must **serialize across sessions**,
and every utterance must **name its session**. Neither falls out of per-session daemons for free, and
this is the reason the feature is more than "call `say` from the gate dispatch".

### Scope of "sub sessions" — confirmed: separate muxcode sessions

**Decided by the user, 2026-08-31.** The feature targets **separate muxcode sessions**, each with its
own `BUS_SESSION`, bus dir, and daemon:

| Reading | What it means | Status |
|---------|--------------|--------|
| **Separate muxcode sessions** — each its own `BUS_SESSION`, bus dir, and daemon | Cross-daemon coordination | **CONFIRMED — this is the target** |
| **Spawned worker windows** inside one session | No extra coordination needed — spawns share their parent's bus dir and daemon, so the parent's announcer already covers them | Contained by the above |

The confirmed reading strictly contains the other, so spawned workers are covered without extra work.
**Phase 4 is therefore required, not optional** — it is the phase that makes the confirmed scope
real, and it is the largest one in this spec.

### The environment decides whether this works at all

Verified on this machine rather than assumed:

| Tool | Path | Role |
|------|------|------|
| `say` | `/usr/bin/say` | macOS TTS; renders to device or to file via `-o` |
| `afplay` | `/usr/bin/afplay` | macOS playback of a pre-rendered file |
| `espeak` / `espeak-ng` / `spd-say` / `festival` / `paplay` / `aplay` | **none present** | Linux TTS/playback — absent here |

The repository contains **no audio code of any kind today** — a grep for `say`/`afplay`/`audio`/
`sound`/`bell`/`speech`/`tts` across `tools/` and `scripts/` returns only prose in comments and test
strings. This is entirely new surface, with no in-tree precedent to copy. The closest structural
precedent is the daemon's alert **cooldown** pattern (`daemon.go:796`, 10-minute dedupe window).

**The governing environmental risk is that the sound plays on the wrong machine.** The daemon runs
where the repo is. Over SSH — or in any remote/headless dev box setup — `say` executes on the
*server* and is heard by nobody, while the user's terminal sits silent on a laptop somewhere else.
The feature is then not merely broken but **actively misleading**: the log records an announcement
that no human could have heard.

**Decided by the user, 2026-08-31: refuse on SSH.** When audio cannot reach the user, the
announcement is not attempted — it is reported in text, and the visual announcement carries the
signal alone. Never play server-side "just in case".

#### Detection must happen at announce time, not at daemon launch

The obvious implementation — read `SSH_CONNECTION`/`SSH_TTY` from the daemon's own environment — is
**wrong, and wrong in the dangerous direction**. The daemon is long-lived and its environment is a
snapshot from launch, while attachment is fluid:

| Sequence | Daemon env says | Truth | Result if we trust daemon env |
|----------|----------------|-------|-------------------------------|
| Launched locally, user later attaches over SSH | no SSH vars | audio unreachable | **Speaks to an empty room and logs success** — the exact failure this decision exists to prevent |
| Launched over SSH, user later attaches locally | SSH vars set | audio reachable | Needlessly silent |

The first row is a false "announced", which is worse than silence. So reachability must be evaluated
**per announcement**, against the clients attached *now*.

tmux exposes exactly this. Verified on this machine:

```
$ tmux list-clients -F "client_tty=#{client_tty} session=#{client_session}"
client_tty=/dev/ttys000 session=muxcode
```

So the check is: enumerate attached clients at announce time and determine whether **at least one is
local**. `client_tty` alone does not distinguish local from remote, so the client's own process
environment (reachable via `#{client_pid}`) supplies the SSH markers. Audio is attempted only when a
local client is attached; zero attached clients is also "unreachable", not "assume local".

## Requirements

### Acceptance criteria

- [ ] A gate entering `waiting` produces an audible announcement naming **the session**, and the run and gate it belongs to
- [ ] The announcement is generated by a text-to-speech component from a composed string — not a fixed pre-recorded asset — so gate text can vary
- [ ] A visual announcement fires on the same trigger, and is **persistent** rather than transient — it must still be discoverable by a user who returns after it fired
- [ ] Announcements reach the user regardless of which session they are attached to, and regardless of which session armed the gate
- [ ] **Exactly one announcement per gate arming** — the daemon polls on a 5s cycle and a waiting gate stays waiting; a per-tick re-announcement is the defining failure mode of this feature
- [ ] **A re-armed gate announces again.** Approval is single-use (`graph_exec.go:483` purges the marker on every pass), so a gate re-entered via a loop edge or `graph retry --from` is a genuinely new approval request and must be announced as one
- [ ] **Negative control:** an already-**approved** gate never announces
- [ ] **Negative control:** no other node type announces — `wait_event` in particular is also `waiting` but needs no human
- [ ] **Two sessions arming gates simultaneously produce serialized, non-overlapping speech**, each naming its own session — the cross-session control; a per-session implementation with no coordination fails here
- [ ] **Negative control:** with the TTS backend absent or failing, the daemon is unaffected — no error, no stall, visual announcement still fires
- [ ] Announcement never blocks the daemon poll loop, with an enforced upper bound on time held
- [ ] **The test suite never emits audio**, and this is asserted rather than assumed
- [ ] Muting suppresses audio while leaving the visual announcement intact
- [ ] An unheard gate escalates on a cooldown rather than either going silent forever or repeating without limit
- [ ] **Audio is refused, not attempted, when it cannot reach the user** (SSH-attached, headless, or no client attached) — reported in text, never silently counted as announced, and the visual announcement still fires
- [ ] **Reachability is evaluated per announcement against currently-attached clients**, never from the daemon's launch-time environment — a daemon started locally and later attached over SSH must refuse
- [ ] **Negative control:** an SSH-only session spawns **no TTS process at all** — refusing must be observable as the absence of the call, not merely a quieter one
- [ ] `scripts/test-gate-announce.sh` passes

### Technical approach

**Trigger at the state transition, not at dispatch.** The announcement belongs on the
`GraphNodeWaiting` transition for `NodeWaitHuman`, alongside the existing `graph-gate-pending`
lifecycle write (`graph_exec.go:496`). That point already has `session`, `run.ID`, `n.ID`, and the
interpolated `prompt`, which is exactly the payload an utterance needs. Announcing from the *render*
path instead would tie a global side effect to whether a pane happened to redraw.

**Once-per-arming via a marker, not via daemon memory.** The gate already writes a `pending` marker
file under `graphApprovalsDir()`. An `announced` sibling marker gives idempotence that survives a
daemon restart — in-memory dedupe would re-announce every gate on restart, and the daemon restarts
routinely (twice in the session that produced this spec). The marker must be purged on the same line
as the `approved` marker so a re-armed gate announces again.

**Cross-session serialization via a machine-scoped lock.** Per-session bus dirs cannot coordinate,
so the announcer needs one lock outside them — a lockfile at a fixed machine path, acquired for the
duration of an utterance and released after. A session that cannot acquire it **queues briefly and
retries**, rather than dropping the announcement or speaking over the holder. Queue depth needs a
cap: five gates arming at once should not produce ninety seconds of continuous speech.

**TTS behind an interface with a null implementation.** A small `Announcer` interface with `say`
(macOS), and a **no-op** used whenever no backend resolves. The no-op path is what makes every
"degrades cleanly" criterion testable, and what keeps CI silent. Backend resolution and the mute
check happen **before** any process spawn.

**Never in-process, never blocking.** The utterance is a detached child with a hard timeout. The
daemon's 5s cycle must not wait on speech synthesis; a wedged TTS process must not wedge the daemon.

**Visual: persistent, not a flash.** `display-message` is transient and is missed by definition when
the user is away — it cannot satisfy the "discoverable on return" criterion alone. The persistent
component should reuse the existing Pending Gates surface plus a durable marker (window/status
indicator), so a user returning after the sound has faded still sees an outstanding gate.

## Implementation

### Phase 1: Trigger and once-per-arming semantics

- [ ] Fire an announcement hook on the `NodeWaitHuman` → `GraphNodeWaiting` transition
- [ ] Write an `announced` marker beside the existing `pending` marker; skip when present
- [ ] Purge the `announced` marker wherever the `approved` marker is purged, so a re-armed gate announces again
- [ ] Emit a `gate-announced` lifecycle event carrying session, run, gate, and backend used
- [ ] Test: one arming → one announcement, asserted across **multiple poll ticks**
- [ ] Test: re-armed gate (loop edge and `graph retry --from`) announces again
- [ ] Test (**negative control**): approved gate never announces
- [ ] Test (**negative control**): `wait_event` and every non-gate node type never announce

### Phase 2: TTS backend and safe degradation

- [ ] `Announcer` interface; `say` backend; **no-op backend** when nothing resolves
- [ ] Compose the utterance: session name first, then run and gate — short by design
- [ ] Detached execution with a hard timeout; daemon never waits on it
- [ ] Reachability check: enumerate attached tmux clients **at announce time**; audio proceeds only when at least one **local** client is attached
- [ ] Treat zero attached clients as unreachable — never assume local
- [ ] On refusal, record that audio was **not** delivered and why, and let the visual announcement carry the signal
- [ ] Test (**negative control**): SSH-attached session spawns **no TTS process** — asserted as absence of the call
- [ ] Test: daemon launched locally, then attached over SSH, **refuses** — pins that the check is not reading the daemon's launch-time env
- [ ] Test: zero attached clients → refuses
- [ ] Test (**negative control**): missing backend → no error, daemon unaffected, visual still fires
- [ ] Test: **the suite emits no audio** — backend forced to no-op under test, asserted
- [ ] Test: a hung TTS process is killed at the timeout and does not delay the poll loop

### Phase 3: Visual announcement

- [ ] Persistent indicator that survives the sound and is visible on return
- [ ] Reuse the Pending Gates surface; do not build a second gate list
- [ ] Indicator clears when the gate is approved or the run ends
- [ ] Test: indicator present while waiting, absent after approval
- [ ] Test (**negative control**): indicator does not appear for runs with no waiting gate
- [ ] Verify against `docs/tui-style.md` — colour is not the only channel, frame clamps to pane

### Phase 4: Cross-session coordination

- [ ] Machine-scoped lock outside any session's bus dir
- [ ] Acquire for the utterance; release on completion, timeout, **and** crash (stale-lock recovery)
- [ ] Bounded queue with a cap on total speech from one burst
- [ ] Every utterance names its session
- [ ] Test: two sessions arming simultaneously → serialized, both heard, neither overlapping
- [ ] Test: stale lock from a killed daemon is recovered, not deadlocked
- [ ] Test: burst of N gates respects the cap and reports what it dropped

### Phase 5: Escalation, mute, and control

- [ ] Re-announce a gate still waiting past a threshold, on a cooldown with backoff
- [ ] `MUXCODE_ANNOUNCE_DISABLE` hard kill switch; runtime `muxcode announce mute|unmute`
- [ ] Quiet hours
- [ ] `muxcode announce test` — verify audibility without arming a real gate
- [ ] `muxcode announce status` — backend, mute state, whether audio can reach the user
- [ ] Test: muted → no audio, **visual still fires**
- [ ] Test (**negative control**): escalation does not fire for an approved gate

### Phase 6: Integration test

- [ ] Create `scripts/test-gate-announce.sh` — hermetic: scratch bus, scratch tmux session, private tmux server, pinned lifecycle dir, **backend stubbed to a recorder script** so nothing audible plays
- [ ] A real graph run reaching a gate announces exactly once, with the session named
- [ ] Poll several ticks with the gate still waiting → still exactly one announcement
- [ ] Approve, re-arm via a loop edge → announces again
- [ ] **Two scratch sessions arm gates simultaneously → recorder shows serialized, non-overlapping calls** (the cross-session control)
- [ ] Backend removed → run completes, daemon healthy, `gate-announced` records the degradation
- [ ] **SSH-attached client → recorder stays empty** (no TTS process spawned) while the visual indicator still appears — the refuse-on-SSH control
- [ ] Zero attached clients → refuses, and says so in the lifecycle record
- [ ] Muted → recorder empty, visual indicator still present
- [ ] Coverage floor so a skipped run cannot report green
- [ ] Run the script and confirm all checks pass

## Risks

| Risk | Why it matters | Mitigation |
|------|----------------|------------|
| **The test suite starts talking** | A backend selected by environment sniffing will find `say` on any developer Mac. A suite that speaks on every run gets the feature disabled within a day | No-op backend under test, asserted by a dedicated test; resolution never defaults to a live backend without explicit opt-in |
| **Sound plays on the wrong machine** | Over SSH the daemon speaks to an empty room and logs success — worse than silence, because the log now lies | **Decided: refuse.** Reachability checked per announcement against attached tmux clients — *not* the daemon's launch-time env, which goes stale the moment attachment changes; report unreachable in text; `announce status` states plainly whether audio can reach the user |
| **Overlapping speech across sessions** | Two utterances at once convey less than one | Phase 4 lock; every utterance names its session |
| **Notification fatigue** | Over-announcing gets the whole feature muted, taking the *visual* signal down with it if they share a switch | Once-per-arming; backoff; **mute is audio-only by criterion** so the visual survives |
| **TTS latency stalls the daemon** | Synthesis is not instant; the poll loop is 5s | Detached, hard timeout, never awaited |
| **Marker drift re-announces on restart** | In-memory dedupe would re-announce every waiting gate whenever the daemon restarts — routine | `announced` marker on disk beside `pending` |
| **Linux/CI has no backend** | Feature must not become a platform requirement | No-op backend is a first-class path, not an error case |
