## Test audit

Adapted from openclaw's `test-audit` skill for muxcode: Go stdlib tests, bash integration scripts, and a fleet where the edit agent never runs a suite itself.

> **The mechanical check — before adding any test function or script section.**
> Write down one sentence for each of the four gate questions below. **If any
> answer is empty, "for coverage", or restates the function name, do not add
> the test.** Then name the one-line change to production code that would make
> it fail — if you cannot, the test cannot fail and protects nothing.

A test is a cost: it is read, run on every build, and edited on every refactor. It earns that cost only by failing when behaviour a caller depends on breaks. More tests is not more safety; a suite padded with tests that cannot fail trains everyone to trust green.

### Three modes

| Mode | When | Output |
|------|------|--------|
| **Authoring gate** | Writing or changing any test | The test is added only if it passes the gate and the junk check |
| **Audit sweep** | Reviewing a diff, or a test file the change touches | Findings: delete, merge, or strengthen — with evidence |
| **Campaign** | User asks to prune a package or subsystem | One PR per package, each with the evidence table below |

Sweeps and campaigns are **user-initiated**. Do not start pruning tests a task did not touch — that is scope creep, and a deletion diff buried in a feature change is unreviewable.

### Authoring gate — four questions

1. **Observable behaviour** — what behaviour, invariant, or consumer-visible contract (on-disk format, CLI output, bus message shape) does it protect?
2. **Credible regression** — what realistic change makes it fail? Name the line.
3. **Coverage gap** — why does no existing test already fail on that change? `grep` the package for the function and the incident before writing.
4. **Production seam** — does it need a hook no production caller needs?

On question 4: a seam that replaces an **external boundary** — tmux, the network (`*http.Client`, `newPipeServer`), the clock, a subprocess — is legitimate, and muxcode is built on them (`tmuxRunner`, `LookupSpawnWindow`). A seam that exists only so a test can reach **internal** state is not: test through the boundary instead.

### Junk patterns — rejected unless they guard a named contract

| Pattern | Why it fails the bar |
|---------|---------------------|
| Assertion-free probe | Runs code, checks nothing; passes whatever the code does |
| Self-comparison / identity | `got := f(x); want := f(x)` — the code is its own oracle |
| Expected value produced by the code under test | Same as above, one step removed (golden files regenerated by the function they test) |
| Copied fixture or manifest | Asserts a file equals a copy of itself; fails only on intended edits |
| Exact source or string grep | Pins spelling, not behaviour; breaks on every rename |
| Duplicate invocation of one contract | Two tests failing on the same line change — keep the one closest to the caller |
| Test-only export kept alive by its test | Dead code with a bodyguard — delete both (see `code-optimizer`) |
| Mock that implements the asserted behaviour | The fake decides the outcome, so the test checks the fake |
| Capability restatement | Asserting a declared flag or constant equals itself |
| Pass count as proof | "19 passed" says nothing if the discriminating assertion was unreachable |

**Negative controls are not junk.** A degradation or guard test must be paired with its opposite — the case where the guard must *not* fire — or a guard that always fires passes it (`tui-style`, and the repo's standing rule). A negative control is the second half of one contract, not a duplicate.

### The deletion test for a new test

Before finishing, ask of each test you wrote: **would it still pass if the feature were deleted or moved?** muxcode's history is full of green tests that could not fail:

- A launcher test suite stayed green with the whole attach-road refresh call removed — it counted calls instead of asserting their order.
- A wrap width-clamp test used short labels, so it never overflowed and never exercised the clamp.
- A chrome-guard test used `jest.config.js`, which no pattern covered, so it could never catch the `pnpm exec eslint test.config.js` misfire.

Each was caught by review, not by its author. Run the check yourself: mentally revert the production change and trace whether an assertion trips.

### Behaviour-preserving refactors

A refactor that keeps behaviour but forces test edits reveals **implementation coupling** — the test pins *how*, not *what*. That is a reason to rewrite the test against the boundary, not to delete it, and never a reason to weaken the refactor.

### Evidence before deleting or merging a test

Record, per candidate, in the PR body or review finding:

| Field | Content |
|-------|---------|
| Test | `file_test.go:Line TestName` |
| Fails on | The concrete regression it catches, or "nothing — explain" |
| Production callers | `grep` result for the covered code outside `_test.go` |
| Stronger proof | The test or `scripts/test-*.sh` section that still fails on the same regression |
| History | `git log -S` on the test — was it added for an incident? An incident test is kept unless the stronger proof covers the same incident |
| Unlocked deletions | Production code or seams now callerless |
| Risk | What goes unguarded if the proof is wrong |

A test named after a dated incident (`2026-09-08 20:31:51`) is presumptively load-bearing. Delete it only when the stronger proof reproduces the same payload.

### Validation — delegated, never local

The edit agent never runs `go test` — delegate:

1. `muxcode send test test "Run tests; confirm <TestNames> ran and passed"` — name the tests, so a filtered-out test cannot hide behind a green package
2. For a removed assertion, name the integration script that still covers the behaviour and delegate it to the **run** agent
3. `gofmt -l` on changed files, then `muxcode send review review "..."`
4. Report production and test line deltas separately — a change that shrinks production code by growing tests needs saying

### Integration scripts

`scripts/test-*.sh` sections follow the same gate. Every script carries a **coverage floor** so a skipped section cannot report green; when you delete a check, lower the floor in the same change and say why, or the next run fails honestly.

### Handoff

Report: what each new or removed test protects, the regression it fails on, any production seam added or removed, test vs production LOC, and follow-ups the audit found but did not act on (named, not silently dropped).

### Review checklist

| Finding | Severity |
|---------|----------|
| New test passes with the feature reverted, or its discriminating assertion is unreachable | must-fix |
| Guard or degradation test with no negative control | should-fix |
| Mock or fixture decides the asserted outcome | should-fix |
| Test-only production seam reaching internal state | should-fix |
| Test deleted without the evidence table | should-fix |
| Duplicate of an existing test on the same contract | nit |
| String or source grep standing in for behaviour | nit |
