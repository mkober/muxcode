# MuxCode

Multi-agent coding environment built on tmux, Neovim, and Claude Code. Each agent runs in its own tmux window, coordinated through a file-based message bus.

## Tech stack

| Layer | Technology |
|-------|------------|
| Launcher | Go (single `muxcode` binary) |
| Hooks | Bash |
| Bus binary | Go 1.22 (stdlib only, no external deps) |
| Agent definitions | Markdown with YAML frontmatter |
| Terminal multiplexer | tmux >= 3.0 |
| Editor | Neovim |
| AI CLI | Claude Code (`claude`) |

## Directory structure

```
scripts/                      # Hook scripts, utility scripts, pollers
agents/                       # Default agent definition files (.md)
agents/harness/               # Simplified agent definitions for local LLM harness
skills/                       # Default skill definition files (.md)
config/                       # settings.json, tmux.conf, nvim/ (managed nvim config)
config/nvim/                  # Neovim config loaded via NVIM_APPNAME=muxcode
├── init.lua                  # Full lazy.nvim config (Dracula, treesitter, render-markdown, telescope)
└── plugin/startscreen.lua    # MuxCode start screen (logo, agents, shortcuts)
docs/                         # Documentation
tools/muxcode/      # Go module — the bus binary
├── bus/                      # Core library
├── cmd/                      # Subcommand handlers
├── daemon/                   # Bus daemon — inbox poller + trigger file monitor
├── tui/                      # Dracula-themed dashboard TUI
└── main.go                   # Entry point
tools/muxcode-llm-harness/    # Go module — standalone local LLM harness
├── harness/                  # Core library
└── main.go                   # Entry point
```

## Build, test, install

| Command | What it does |
|---------|-------------|
| `./build.sh` | Runs `make install` — builds Go binary, installs agents/configs — then `muxcode upgrade-daemons` so all running session daemons re-exec the new binary |
| `muxcode upgrade-daemons [--dry-run] [--force] [--session <name>]` | Restart running session daemons/monitors on the installed binary — a long-lived daemon otherwise keeps the code from its launch. Version-aware: each daemon records its build in `daemon.version` at startup, and one matching this binary (`Info.SameBuild` — version, commit **and** date, so a dirty rebuild still cycles) is skipped unless `--force`. `--dry-run` names both sides per session; `--session` scopes to one daemon. Kills orphan daemons whose tmux session is gone. Runs automatically on two roads: `build.sh` after `make install`, and `muxcode <dir>` when it attaches to an **already-running** session, scoped to that session alone (`MUXCODE_AUTO_UPGRADE_DAEMONS_DISABLE=1` opts out). A fresh `LaunchSession` always starts its daemon from the binary on PATH, so attaching is the only road on which one drifts behind an install — and a session is launched once but attached many times. The attach check is also the road that survives MUX-161: `build.sh`'s call runs in the build agent's sandbox where `ps` is denied, while attaching runs in the user's own terminal. Discovery is `ps` when it runs; where it cannot (a Codex build sandbox), the processes the kernel reports holding each bus directory's `lock/daemon.owner` and `lock/monitor.owner` record locks (`bus.AcquireInstanceLock`, which keeps the `daemon.lock` flock every version takes for single-instance exclusion), never a pid file's contents — a `daemon-discovery-ps-failed` info row. With `ps` the processes are killed and relaunched (output kept in the bus directory's `upgrade-relaunch.log`); without it nothing is killed or orphan-killed — `lock/daemon.restart` and `lock/monitor.restart` restart requests make each re-exec the installed binary itself, because a process started from inside a Codex sandbox dies with it (live-checked 2026-11-14). Either way a restart counts only when the replacement holds its owner lock under the expected pid and has stamped the installed build (`daemon.version`, new `monitor.version`) since the rollout began, within 20 s. A live daemon in the rollout's own session (`--session`, else `BUS_SESSION`) left on an older build, or a restart that cannot be proved (an unhonoured request is withdrawn, the old processes left running), writes `daemon-upgrade-failed` with the reason and exits 1, so `build.sh` prints its warning; `muxcode session status` ends with a `Daemon:` line naming a stale build and the fix |
| `muxcode upgrade [--check] [--force] [--json]` | Self-upgrade from the latest GitHub release (MUX-202), no checkout needed: Check (`releases/latest`; verdict current/ahead/newer/unknown via `CompareSemver` — a dev build past the tag is **ahead**, never downgraded unless `--force`), Download (source tarball to `$XDG_CACHE_HOME`/`~/.cache/muxcode/upgrade/<tag>/`; `download.json`, written last, marks a cache hit), Build + Install (`make build` then `make install`, one `VERSION`/`DATE`, explicit absolute `BINDIR`/`CONFIGDIR`), Verify (`<BINDIR>/muxcode version --json` must report the tag **and** be the `muxcode` on PATH), Restart daemons (the **new** binary's `upgrade-daemons`, BINDIR first on its PATH — never in-process), Reload tmux config. One per-user lock (`~/.config/muxcode/upgrade.lock`) serializes runs; each step writes an `upgrade-*` lifecycle row. `--check` exits 0 / 10 newer / 1. The **Check for Updates** modal (`prefix + b`, `U`; `muxcode upgrade-ui`) runs it as a detached `upgrade --events` child bound to what was confirmed (`--expect-tag`, `--expect-session`), so `q` closes the modal and the upgrade carries on |
| `./test.sh` | Runs `go vet ./...` then `go test -v ./...` in **every** module under `tools/` (`muxcode`, `muxcode-llm-harness`), stopping at the first failure. Always ends with `=== Summary ===`: one `<module>: passed \| failed (go vet) \| failed (go test) \| never executed` line per module, then `modules=<n> ran=<n> passed=<n> failed=<n> never-executed=<n>` — so a truncated run names the modules it never reached rather than reading as a shorter green one (MUX-174). A failed module's line is followed by indented detail lines naming the failure — `  log: <path>`, then `  FAIL <package>: <tests>` (at most four) or `  vet <finding>` (at most three) — inside the summary, the part a history row keeps; each module's full vet and test output is saved under `$MUXCODE_TEST_LOG_DIR` (default `/tmp/muxcode-test-logs/<run>/<module>.log`), because twice on 2026-11-13 a failure passed on rerun and nothing named the test (MUX-215). Exit 0 only when every module passed; 1 on any failure, or when `tools/` holds no module |
| `muxcode version [--json] [--at-least vX.Y.Z]` | Print the stamped identity; `--version`/`-v` print the same and never route to the launcher. `--at-least` exits 0 (at or past), 1 (older), 2 (uncomparable — an untagged dev build) for script preconditions. Stamped via Makefile `-X` ldflags from `git describe`; unstamped builds fall back to Go's VCS info, then `devel` |
| `make build` | Builds Go binary to `bin/muxcode` (prints the stamped version) |
| `make install` | Build + install binary to `~/.local/bin/`, agents, skills, configs to `~/.config/muxcode/` |
| `make clean` | Remove `bin/` directory |
| `./install.sh` | First-time setup — checks prereqs, builds, configures tmux and Claude Code hooks |
| `git push origin vX.Y.Z` | A `v*` tag push runs `release.yml`: `./test.sh` gate → darwin/linux × amd64/arm64 stamped via `make build VERSION=<tag>` → `sha256sums.txt` → `gh release create --generate-notes`. `gh workflow run release.yml -f tag=vX.Y.Z` publishes an already-pushed tag. Manual tagging stays user-approved, via the commit agent |
| _(automatic)_ | `.github/workflows/auto-release.yml` cuts a patch release on every merged PR: next `vX.Y.Z` from the latest release tag, tagged on the merge commit, then `release.yml` via `workflow_call` — **not** the `v*` push trigger, because a tag pushed with `GITHUB_TOKEN` raises no workflow event. **Label a PR `skip-changelog` to cut no release** (docs and backlog churn carry it, so the version tracks shipped code). Triggered on `pull_request`/`closed` so labels are on the payload; a direct push to main cuts nothing. A `concurrency` group stops simultaneous merges computing the same tag |
| `bash scripts/release-labels.sh` | Idempotently creates the five labels `.github/release.yml` reads: `breaking`, `type:feature`, `type:defect`, `docs`, and `skip-changelog`. A GitHub mutation, so route it through the commit agent |

## Code conventions

### Go (bus binary & harness)

- PascalCase for exported identifiers, camelCase for unexported
- Stdlib only — no third-party imports
- Tests in `*_test.go` files, same package (not `_test` suffix)
- Bus directory path: `$XDG_STATE_HOME/muxcode/bus/muxcode-bus-{session}/` (default `~/.local/state/muxcode/bus/…`; `BusDirBase`/`BusDir` in `bus/config.go`). Never `/tmp` — macOS's `tmp_cleaner` deletes files there untouched for three days, which lost a gated graph run's `graph.json` (MUX-208). `MUXCODE_BUS_BASE` (absolute) overrides the base; an unresolvable home panics rather than fall back. The launcher, daemon and every `agent launch` export the resolved directory as `MUXCODE_BUS_DIR`, and `muxcode bus-dir [session]` prints it — scripts read one of those (`scripts/lib/muxcode-bus-dir.sh`), never compute the path. A legacy `/tmp/muxcode-bus-{session}` is moved on first resolution, session launch or daemon start (`MigrateLegacyBusDir`, one `bus-dir-migrated` row; if both exist the new one wins, `bus-dir-conflict`). Spawn worktrees live under `StateDir()/spawn/{session}`. Stays in `/tmp` deliberately: the analyze trigger, the preview temp file and the Codex package caches
- **No test may bind a socket** — use `newPipeServer` (both modules), never `httptest.NewServer`. A sandboxed agent cannot listen, so a socket-bound test panics before any assertion and `set -e` then hides every later module. Production code takes an optional `*http.Client` (nil in production) as the seam

### Bash (hooks & utility scripts)

- `set -euo pipefail` for build/test/install scripts (`build.sh`, `test.sh`, `install.sh`)
- Hooks do NOT use `set -e` — they exit gracefully on errors
- 2-space indentation
- `snake_case` for functions, `UPPER_CASE` for environment variables
- JSON parsing: `jq` primary, `python3` fallback

**Editing pitfalls:**

- **Vim `sil!` in pipe chains**: `sil!` suppresses only the command immediately after it, not the whole `|` chain — every command needs its own prefix (`sil! cmd1 | sil! cmd2`), or an E35 raises a "Press ENTER" prompt that breaks the commands after it.
- **Diff preview jump-to-line**: send as a separate `tmux send-keys` after a 150ms sleep, since scrollbind must be active before jumping. Use `norm! {LINE}Gzz`, not `:N` — only `norm!` syncs scrollbind across both diff panes.
- **Process substitution in tool profiles**: `Bash(diff *)` does NOT match `diff <(...)` — Claude Code treats `<()` as a special construct requiring explicit `Bash(diff <(*)`.
- **tmux send-keys text + Enter**: two separate calls with a ~100ms delay. Claude's TUI drops an Enter arriving in the same pty write as the text before it, leaving the agent with a full input buffer it never submits.
- **tmux send-keys Escape before a payload**: never adjacent to the text or the Enter it precedes — route it through `bus.TmuxDismissOverlay` (Escape → gap → `C-e` absorber → gap). A TUI key parser holds a bare `ESC` pending and fuses it with the next byte into a Meta chord, so `Escape` typed straight into `hello` submits `ello` and a one-character payload vanishes entirely (MUX-163; measured escape window 30–50 ms on claude 2.1.258). The absorber key takes the fusion; a gap alone does not fix it — it is a bet on the receiver's escape window, a constant muxcode does not own.

### Agent definitions

- YAML frontmatter with `description:` field (extracted by `ExtractFrontmatter()` in `bus/launch.go`)
- kebab-case filenames (e.g. `code-editor.md`, `git-manager.md`, `dev-server.md`)
- Role-to-filename mapping in `AgentFileName()` in `bus/launch.go`

### Documentation

- 2-space indentation in markdown
- Title Case for H1, Sentence case for H2+
- Prefer tables and code blocks over prose
- Cross-link docs with relative paths (e.g. `docs/architecture.md`)
- When updating docs, augment existing content — don't rewrite or reorganize
- Feature requirements live in `docs/requirements/` — completed specs in `completed/`, in-progress drafts in `drafts/`, planned/parked specs in `backlog/` (indexed by [`backlog/backlog.md`](docs/requirements/backlog/backlog.md))
- Each backlog spec carries a stable id from the backlog index, used in its filename, branch (`<id>-<slug>`), issue and PR titles
- **Integration test phase required**: every requirements doc MUST end with an integration test phase containing either automatable checkbox steps (`- [ ] Reload build+test agents → verify config changed`) or a step to create `scripts/test-{feature}.sh`. It validates end-to-end behaviour, not just units.

### Permissions (`.claude/settings.local.json`)

- **No hardcoded user paths**: this is open source — never add absolute paths carrying a username or home directory. Use relative (`tools/muxcode/...`) or generic (`~/.config/muxcode/...`) forms.
- User-specific `Read()` permissions for external dirs (nvim plugins, dotfiles, etc.) belong in the user's global `~/.claude/settings.json`, not in the project-local file.

## Key constraints

- **Edit agent delegation**: never runs build, test, deploy, dev servers, API requests, log tailing, AWS commands, git (even `git status`) or `gh` — everything goes through the bus, enforced by the `muxcode hook guard` PreToolUse hook on Claude and by `DenyTools` plus the daemon pane audit on OpenCode. Routing: **serve** dev servers; **run** AWS execution and ad-hoc scripts (`scripts/test-*.sh`); **watch** log tailing only; **api** API testing (`prefix + i`); **commit** with action `pr-read` for PR reads (never review); **plan** with `update-docs` for all docs and for Jira/Confluence — `CheckDocFileGuard` blocks edit from `docs/**/*.md` (root `CLAUDE.md`/`README.md` stay editable). `MUXCODE_EDIT_CLI=opencode|claude` switches edit's provider. See [Architecture](docs/architecture.md).
- **Atlassian authority**: reads are open to every role; writes are gated to plan alone (`CheckAtlassianAuthority` at the CLI, `CheckAtlassianMCPGuard` on MCP). Plan writes only on an explicit user request relayed from edit, never as a side effect of a docs change — edit is the consent boundary, plan the write boundary. `MUXCODE_ATLASSIAN_AUTHORITY_ROLES` overrides the list; empty denies every role.
- **Plan agent scope**: plan (F1) writes only `docs/`, `CLAUDE.md` and `README.md`; it reads source but never writes elsewhere. It also owns GitHub issues: the plan guard carves `gh issue create/edit/delete/close/reopen/comment/view/list/status` (`planGitHubIssueVerbs`, `bus/hook.go`, a single unchained statement only) out of its `gh` block, and writes follow the Atlassian rule — only on a user request relayed from edit (`issue-write`) — with one standing exception: filing a new defect spec also finds or creates its GitHub issue and links it on the spec's `**Tracking:**` line. Every other `gh` command stays with commit. The hosted `docs` role maps to plan. F1 also hosts **research** via mode cycling — its own inbox, no chain; it web-searches references and delegates implementation to the active F2 agent.
- **Spec verification**: after review the daemon sends plan `verify-spec` for the active spec (`muxcode spec set <path>`); plan ticks criteria and phase steps, updates status, reports to edit, and upserts a `## Time Tracking` row keyed by branch from `muxcode branch-time show` — absolute totals, never-regress (re-seed with `branch-time seed`, never `--add`). Gated by `NotifyPlanOn` on the review chain (default `["success"]`) against **this review's own verdict** — the last `EXIT=<n>` sentinel in the reply that tripped the reviewed marker (`bus.ReviewReplyOutcome`, `bus/review_verdict.go`). No sentinel, or `EXIT=0` beside a findings line counting a must-fix, is an unknown verdict and withholds; every withheld fire writes `plan-verify-withheld <outcome> <review-id> (<evidence>)` and leaves the movement marker unwritten, so a later passing review still fires, while the reviewed transition happens either way. Review history rows are not read — they carry no reply id and review logs after it replies, so a row cannot be attributed to a reply. Before MUX-172 the gate was asked about a literal `"success"`, so `["success"]` and `["*"]` behaved alike and plan was sent to verify against reviews returning must-fixes, four times on 2026-09-09. The pointer survives session re-init like `graphs/` (a `spec-kept` row); it is removed only by `muxcode spec clear` or a failed graph launch rolling back the pointer it wrote (`UnpointSpecForLaunch`); every pointer write writes a `spec-set`/`spec-clear` row naming actor and path (`LogSpecPointerChange`; launch, rollback, branch and picker writes add `via=`, the close-out repoint logs `spec-repoint`), and an unset pointer under a running `RequiresSpec` run raises `spec-unset-live-run` to edit — before MUX-168 every relaunch purged it under a live run, which `loop-check` read as no phases remaining.

A bare `scripts/test.sh` matches a path-carrying pattern by basename, as its `bash` form does (`matchPatterns`); `swift --version` stays unclassified. Nor is an **unfinished call** evidence: Claude completes a `run_in_background` Bash call — and a foreground one it backgrounds on timeout — at dispatch, firing `PostToolUse` then with a `backgroundTaskId` and no exit status, and fires no hook when the task ends. `backgroundLaunch` makes such a call write no row and name no chain, logging `chain-withheld` instead, and completion it cannot read fails closed. - **User-initiated commits**: commits, pushes and PRs are never auto-triggered; the chain stops at review. Commit only when asked or when a complete logical unit is finished — no micro-commits.
- **Attribution stripping**: `LaunchSession()` installs an idempotent `commit-msg` hook (`InstallCommitMsgHook()`) that strips `Co-authored-by` trailers; it chains with existing hooks and respects `core.hooksPath`.
- **Session-start init** (MUX-207): before any agent launches, `LaunchSession` runs `InitProjectFiles` (`bus/project_init.go`) on `DetectProject`'s result and creates whichever is missing of `.muxcode/config` (the build, test and precheck patterns), `.claude/settings.json` (read-only toolchain queries only — edit is the one role that reads Claude permissions, and its guard refuses builds) and a `CLAUDE.md` stub (skipped when `.claude/CLAUDE.md` exists). - **Auto-CC**: messages from build/test/review/deploy to non-edit agents are copied to edit; chain and subscription messages use `SendNoCC()`.

- **Edit inbox**: `--wait` blocks for the response (`MUXCODE_INBOX_POLL_TIMEOUT`, default 600s); `--track` returns at once and the daemon wakes the sender when the response lands. Both record a task under `tasks/` (`muxcode tasks`).
- **Delegation message hygiene**: sends are short, single-line and intent-level — `validatePayload()` warns on newlines or >500 chars, and such a payload misses the `Bash(muxcode *)` glob and prompts instead of delivering. Delegate intent, not pre-baked commit messages or file lists. Prefer `--track`; `--wait` only when the result is needed next. Re-requests must state what changed — an identical re-send reads as a duplicate. Long content goes in `/tmp/<name>.md` with a one-line pointer. Reply IDs are looked up, never reconstructed; a reply whose action does not match your request is suspect. See [Agent Bus CLI](docs/agent-bus.md#muxcode-send).
- **Keep agents deliverable**: the daemon delivers only to idle agents, so never run a blocking command (`gh pr checks --watch`, `tail -f`, interactive watchers) in an agent's own pane — route it to **watch** or a background `muxcode proc`. Recovery: busy → returns to idle on its own; at the prompt but stuck (dropped Enter, stale markers, parked input) → `muxcode deliver <role> [--force]`, never a hand-rolled `send-keys "You have new messages" Enter`; genuinely frozen TUI → kill the OS process (`-TERM`, then `-KILL`) and let the daemon restart it; a Claude agent dead at its shell → `muxcode resume <role>` relaunches it into its conversation with the full launch flags (`--force` exits a live one first; not `muxcode session resume`, which prints memory summaries).

- **PII scrubbing** (MUX-179, MUX-203): coverage differs by road. **History** — every writer of `<role>-history.jsonl` (hook capture, synthesized reply rows, `muxcode log`, `muxcode agent`) redacts by `ScrubForRole` (`bus/scrub.go`): credentials for **every** role, PII (emails, SSN, cards, phones, DOB) as well for `api`, `run`, `runner`, `watch` — PII patterns match ordinary output (a commit's author email), credentials match precisely. A credential is a JWT, an AWS key, an `Authorization:` header with a `Bearer`/`Basic`/`Token` scheme (its token) or `Digest` (its whole field list, to end of line), a value after `=`/`:` — a quoted JSON key included — whose label contains `api_key`, `api_secret`, `auth_token`, `token`, `secret`, `password`, `passwd` or `authorization`, or a bare `key=` whose value is secret-shaped (16+ characters mixing letters and digits, no `.` or `:`, not a path — so `key=timestamp`, `partition_key=…` and an SSH fingerprint stay). Every writer strips ANSI escapes before matching, since a color code between a label and its `=` defeats the pattern; hook capture scrubs the whole response before its line tail and length clip (both keep the end, where a command prints its verdict — `clipOutput`, MUX-215), `muxcode agent` before its length cap, and reply rows and self-reports are stored whole. Every road scrubs a result whole, never line by line. Where the PreToolUse guard runs — Claude and hook-road Codex, not OpenCode or scrape-road Codex — it denies a bare `env`, `printenv`, `ps eww`/`e`/`-E` or `cat` of a muxcode config on those roles unless it pipes straight into a bare `muxcode pii-scrub` — any argument, `--role build` included, does not count — and `printenv NAME` even piped (`CheckPIIPipeGuard`, `bus/pii_guard.go`). **Not covered**: scrape-road Codex (no hook runs, not even the guard), a Claude Bash call that exits non-zero, non-Bash tool results (`Read`), provider on-disk records (`opencode.db`'s WAL, a Claude transcript after a non-zero exit, Claude's own telemetry), a history row's `Command`/`Description`, and bus message payloads (`inbox/`, `log.jsonl`). A daemon-relaunched agent whose pane then shows Claude's definition-unavailable banner is **stopped** (stop marker) and an `agent-resume-unrestricted` alert raised (`refuseUnrestricted`) — it must never run on default tools (MUX-136). A failed pane capture **defers** that verification rather than clearing it (`agent-resume-verify-deferred`), and a failed stop leaves the role `pendingStop`, retried each sweep ahead of the stop-marker skip, so `checkAgentHealth` cannot resume it straight back. A failed capture defers recovery with the check still pending (`agent-resume-verify-deferred`); a failed stop keeps the role `pendingStop` — checked ahead of the stop-marker skip, never recovered or restarted, retried every sweep (`agent-resume-stop-failed`) — and edit is told "stopped" only once it is. `MUXCODE_AUTO_RESUME_DISABLE=1` restores the old fresh-relaunch behaviour exactly; manual `muxcode resume` is unaffected. See [Configuration](docs/configuration.md).
- **Daemon watchdogs** (each opt-out by env, each logging lifecycle events): long-active (`MUXCODE_ACTIVE_WATCHDOG_SECS`, 600); stuck-provider reload (`MUXCODE_STUCK_RELOAD_DISABLE=1`; cap 3/role); in-flight task expiry (`task-timeout`, 600s — expired tasks no longer block the dedup guard); permission-block (`MUXCODE_PERMBLOCK_WATCHDOG_DISABLE=1`; alert-only, stops re-waking a Claude agent wedged at a rejected permission prompt); codex-approval (`MUXCODE_CODEX_APPROVAL_WATCHDOG_DISABLE=1`, 15s — answers a read-only Codex role's command-approval prompt with Escape, the prompt's own "No"). That last one **acts** rather than alerts because the prompt is an *escalation* request — `-a on-request` is an approval policy, not a sandbox or an allowlist, so in-sandbox commands never raise it and only an attempt to work outside does — and the roles it is given to (`isReadOnlyCodexRole`: review, analyze) are told not to execute at all, so no human at the pane would ever say yes. **The approval policy is not what enforces that prohibition**; the role instructions are, and the watchdog only catches the escalation attempts that slip past them. Unlike permission-block it needs no pending inbox, since the agent parks *mid-turn* showing neither spinner nor ❯ — invisible to every other road until the 600s task timeout records the node `timed-out`, naming the clock instead of the cause (2026-09-14, is-operations-gateway: a review node burned 602s at a prompt asking to run Playwright outside its sandbox, then looped). Detection is tail-anchored (`codexApprovalPromptLive`) like the trust prompt and for the same reason — Codex draws it inline, so matching the marker alone would fire an Escape, Codex's interrupt, into every later turn. **No road re-drives a working pane**: `PaneShowsRecoverableIdle` (❯ present *and* not thinking) gates the stall watchdog, and the provider-aware `AgentIsWorking` refuses at `ForceDeliver` entry — above the unnotified-inbox branch, so an ordinary pending row is withheld mid-turn too — and inside `RedriveTask`, so `deliver --force`, receipt-gap recovery and remote inherit it. A busy pane is a **skip** (nil error, `Skipped` set), never the idle gate's error: `--force` overrides the idle-prompt gate and never this one — the injection's Escape preamble is Claude's interrupt key, and on 2026-09-09 the watchdog killed the run agent's integration script twice, 61s apart, because `PaneHasIdlePrompt` reads a composer that renders mid-turn (MUX-171). Code: `bus/stuck.go`, `bus/deliver.go`, `daemon/daemon.go`.
- **Daemon self-monitoring**: `daemon.keepalive` is stamped each poll; `muxcode watch --monitor` relaunches a daemon stale for >30s.
- **Local LLM harness** (`tools/muxcode-llm-harness/`): three-layer circuit breaker (turn filter, `MaxAllBlockedTurns=2`, `MaxConsecutiveFailures=3` → 30s cooldown; 5-minute batch timeout); build and test are single-shot roles; definitions resolve `agents/harness/` > `.claude/agents/` > `~/.config/muxcode/agents/harness/` > `~/.config/muxcode/agents/`. See [Agents](docs/agents.md#circuit-breaker).

### Bash scripts

- Hooks consume JSON from stdin via `cat` — parse with `jq` or `python3`
- Preview hook detects edit window via `tmux display-message -p '#W'` — exits immediately if not `edit`
- Analyze hook writes trigger file at `/tmp/muxcode-analyze-{session}.trigger` — format: `<timestamp> <filepath>` per line
- Integration scripts assert their binary precondition through `scripts/lib/muxcode-version.sh` — `require_muxcode_version "$MUX" vX.Y.Z <spec-id>` wraps `muxcode version --at-least`: an older binary fails (exit 1), while an untagged dev build has no semver rank (exit 2) and continues with a note, so the tree-built binary developers run between tags stays testable. A binary predating `muxcode version` routes it to the launcher as a project path and exits 1 — read as "older", correctly

### Agent definitions, skills, context

- **Agent files**: 3-tier resolution: `.claude/agents/` > `~/.config/muxcode/agents/` > defaults. Frontmatter extraction by `ExtractFrontmatter()` in `bus/launch.go`. See [Agents](docs/agents.md).
- **Skill files**: 3-tier resolution: `.muxcode/skills/` > `~/.config/muxcode/skills/` > `skills/`. YAML frontmatter with `name`, `description`, `roles`, `tags`.
- **Context files**: `context.d/shared/*.md` (all roles) + `context.d/<role>/*.md`. Priority: project > user > auto-detected.
- **Tool profiles**: `bus/profile.go` — per-role permissions with `Include` (shared groups), `CdPrefix`, `Tools`. See [Agents](docs/agents.md#tool-profiles).
- **Config files**: shell-sourceable. A `$MUXCODE_CONFIG` naming an existing file is read alone; otherwise `~/.config/muxcode/config` is the base and the project's `.muxcode/config` overrides it key by key (`GetShellConfig`, layered since 2026-11-02 — before, the first file found was read alone, so a project config hid every home setting). Environment variables win over both. `muxcode config set` writes to the first of the three that exists. See [Configuration](docs/configuration.md).
